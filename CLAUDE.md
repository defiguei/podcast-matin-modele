# Podcast du matin — notes de travail

Tout est en français : code, commentaires, messages, commits. L'application tutoie.

## Deux dépôts

- **Le modèle** (`defiguei/podcast-matin-modele`), public et « Template repository » : le code commun. On y code et on pousse directement sur `main`.
- **Les dépôts personnels** (`podcast-matin` de chacun, dont celui du propriétaire) se mettent à jour depuis le modèle : workflow `.github/workflows/mettre-a-jour.yml` (bouton « Mettre à jour » de l'application, ou lancé à la main) qui exécute `mise_a_jour.py`. On ne modifie pas un dépôt personnel directement : ce fichier y est recopié, donc si tu travailles dans un `podcast-matin`, fais le changement dans le modèle.
- Jamais copiés : `memoire.json`, `preferences.json`, `reglages.toml` (fichiers personnels). Les fichiers listés dans `version.json` → `supprimes` sont retirés chez chacun.
- Repères remplacés par le dépôt et l'adresse du bot de chacun : `REPERE_DEPOT` et `REPERE_HOTE` dans `mise_a_jour.py`. Ne les écrire que sous leur forme exacte (jamais échappés, ex. dans une expression régulière) ; dans `mise_a_jour.py` et les tests, les construire en morceaux. Un test vérifie qu'il n'en reste aucun après une mise à jour simulée.
- **Nouvelle version** : `VERSION` et `NOUVEAUTES` (liste) dans `cloudflare/src/etat.js`, même version dans `version.json` (un test compare). Les bots la proposent dans les 24 h. Après le déploiement, la première ligne de `NOUVEAUTES` est annoncée par notification (`annoncerVersion`).
- Le modèle n'a pas de secrets Cloudflare : « Déployer le bot » s'y arrête sur un avertissement. Ne jamais lui en donner (il remplacerait le bot du propriétaire).

## Architecture

- **Bot** (`cloudflare/`) : Cloudflare Worker + Durable Object `Etat` (stockage : `config`, `etat`, `cles`, `texte:*`, `archive:AAAA-MM`).
  - Fichiers des épisodes (`audio.js`) : Durable Object `Audio`, un objet par mois (`2026-10`) plus `voix` pour les extraits ; fichiers en morceaux d'1 Mio (2 Mo au plus par valeur), recollés à la lecture, plages `Range` et `HEAD`. GitHub les dépose par `PUT /api/fichier?nom=AAAA-MM/….mp3` (`liaison.Bot.deposer`) ; s'il ne peut pas, l'épisode (ou la recherche, l'extrait) échoue : rien n'est parti. L'événement `episode` porte `audio` et `pochette`. Lecture : chez le bot seulement (les épisodes d'avant 2026-10-21.4 n'ont plus d'audio).
  - Notifications (`notifications.js`, norme Web Push) : clé VAPID du bot créée au premier besoin (stockage `vapid`), abonnements dans `etat.abonnements` (rattachés à l'appareil, header `X-Appareil-Id` posé par le Worker ; `coupe` = interrupteur de l'appareil, action `notif_couper`, l'abonnement reste). `notifier()` n'envoie qu'aux abonnements non coupés, chiffre (RFC 8291, aes128gcm) et signe (VAPID ES256) ; 404/410 : abonnement oublié. Envoyé à l'événement `episode`, `echec` (envoyé par `podcast.py` en cas d'échec) et `recherche`. Service worker : `/app/sw.js` (portée `/app`). Le test « Notifications » déchiffre réellement les envois du faux service (`/push/<id>` de `faux.mjs`).
  - Un épisode est repéré par `ref` (heure d'envoi HHMMSS) : `cleEpisode` = `ep:date:ref` (`message_id` pour les anciens épisodes, gardé pour leurs clés).
  - Épisodes : les 60 derniers dans `etat.episodes`, les autres dans `archive:AAAA-MM` (action `episodes_mois` de l'application). Chaque nuit (`menageFichiers`) : on garde le mois en cours et les 12 précédents (audio, textes, archives), la place prise (`etat.stockage`) est recomptée.
  - `index.js` routes ; `etat.js` état, planning, tic, API ; `miniapp.js` données de l'application ; `app.html` l'application (une seule page) ; `config.js` modèle des réglages et des rubriques (`RUBRIQUES`, `deroule`, règles R1…, `sourcesAuto`) ; `connexions.js` clés et agendas ; `flux.js` flux RSS privé ; `services.js` GitHub, Gemini, secret partagé ; `comprendre.js` demandes libres ; `icones.js` icônes générées (`test/fabriquer_icones.py`).
  - Application : `/app/api`, ouverte seulement par un appareil autorisé (en-tête `X-Appareil` = jeton donné contre un code à 6 chiffres ; le bot n'en garde que l'empreinte, 8 appareils au plus). Réglages › Application : bloc « Appareils » (`vueAppareils`) avec, par appareil, l'interrupteur de notifications et la croix (`appareil_retirer`, aussi pour l'appareil lui-même : son jeton est effacé).
  - **Demandes libres** (écrites ou vocales, action `parler` de l'application) : un seul appel Gemini (`comprendreCoeur`) renvoie `entendu` (transcription d'un vocal), `operations` et `reponse` ; `appliquerCompris` applique (`comprendre.js` : `appliquerOperations`). Règles : un champ absent n'a jamais de défaut destructeur (`heureDemandee` : heure absente = erreur, reprise si rangée dans `valeur` ; `retirer_pause` sans date ne retire pas tout ; `regler` sur une liste ajoute) ; le message montré vient de `messageCompris` (ce qui a été appliqué ; la phrase de Gemini n'accompagne que des changements réussis ou une demande sans changement) ; un changement `lourd` (couper 3 jours ou plus, ou tout le planning ; supprimer une rubrique) est gardé dans `etat.a_confirmer` (15 min) et attend `parler_confirmer`/`parler_abandonner` (`repondreConfirmation`). `etat.historique` garde les 30 dernières demandes (message ou transcription, opérations, issue), montrées dans « Demande au bot » (`donnees.demandes`).
  - **Rubriques : un seul chemin.** Le catalogue « + » est `MODELES_RUBRIQUES` (`config.js`), envoyé à l'application (`donnees.modeles`) et décrit à Gemini (champ `regle.modele`). Fiche de l'application et demande libre passent par le même formulaire : `formulaireNeuf` / `formulaireDepuisRegle` → `enregistrerRubrique` → `champsDepuisFormulaire` (`miniapp.js`). Une nouveauté de la fiche se répercute donc à la voix ; un nouveau modèle s'ajoute dans `MODELES_RUBRIQUES` seulement.
  - **Recherches ponctuelles** (`periode.type = "ponctuelle"`, onglet Idées) : `recherche.rendu` = `point` (podcast d'état des lieux d'un sujet, `recherche.minutes`, format `point` du workflow Recherche : `recherche.lancer_point`) ou `idees` (sorties, format `ecrit`/`audio`). `lancerRecherche` force `point` pour une rubrique `point`. Demande libre : créer une recherche ponctuelle la lance tout de suite (`nouvelle_regle` → action `resultats`, `formatRecherche`) ; `garderPonctuel` écarte alors `nouvel_episode`, `resultats` et `regler format.duree_minutes` (un podcast ponctuel ne touche jamais l'épisode du jour), et un `nouvel_episode` limité à des recherches ponctuelles devient leur recherche.
  - **Rubriques essentielles** (Agenda, Mes déplacements, Actu locale, À creuser, Actualités : `RUBRIQUES_A_CHERCHER` dans `config.js`, `ESSENTIELLES` dans `recherche.py`, mêmes clés des deux côtés, un test compare) : leur fiche a le menu « ··· » (`menuIntegree`) ; « Supprimer » les met hors des épisodes (`actif: false`, la ligne reste dans « Ton épisode », grisée) et « Ajouter une rubrique » › L'essentiel les remet par interrupteur. « Chercher maintenant » / « Mini-podcast » passent par l'action `recherche` avec la clé comme identifiant : `lancerRecherche` lance `recherche.yml` en `ecrit` ou `point` ; `recherche.regle_essentielle` fabrique une règle le temps de la recherche (mêmes sources que dans l'épisode ; Actualités lit les médias, `ajouter_medias`), `lancer_ecrit_essentielles` envoie le point écrit (événement `recherche`, texte dans `resultats[].intro`). Les identifiants de recherche passent par `identifiants_recherche` (`podcast.py`).
  - **Sources** (Réglages › Sources) : catégories `SOURCES` + `INFOS_SOURCES` (`config.js` : ce qu'elle apporte, où elle cherche, `cle_api`), `config.sources.coupees` (retirées : ni proposées ni lues) et `config.sources.flux` (flux spécialisés `{ id, nom, url }`, cochés comme `flux:<id>`). Une rubrique coche toujours ses sources (au moins une, `champsDepuisFormulaire`) ; chaque modèle a les siennes (`MODELES_RUBRIQUES[].sources`), une demande libre sans source reçoit `sourcesAuto` (affichées et annoncées). Côté épisodes, `regles.sources_lues` : seules les sources cochées et non retirées sont lues (plus d'ajout d'après le titre ; les anciennes règles ont été rendues explicites une fois par `migrerSources`). Trains (suivi et horaires) seulement si « transports » est coché.
  - Test des clés (`connexions.js` : `testerCle`) : Gemini liste les modèles (et ceux de `MODELES_PODCAST`, à garder égaux à `podcast.py`, un test compare), Tavily `/usage` (crédits restants, sans recherche), SNCF `coverage` (fin des horaires). Clé dans l'application : action `cle_tester`, testée par le bot. Clé dans GitHub : le bot lance `tester-cles.yml` (`cloudflare/tester-cles.mjs`, même code, Node sans dépendance) qui renvoie l'événement `cles` ; résultat dans `etat.tests_cles`, la page relance l'état jusqu'au résultat. Un test réussi (encart vert) n'est montré qu'une journée (`quand_ms`, `resumeConnexions`) et s'efface au premier épisode qui suit (événement `episode`) ; un échec reste.
  - GitHub ↔ bot : `/api/*` avec `X-Podcast-Secret` = sha256(`podcast:` + jeton GitHub du bot), 48 premiers caractères (`liaison.secret_partage`, `services.secretPartage`) : `BOT_GITHUB_TOKEN` côté GitHub, `GITHUB_TOKEN` côté bot (le déploiement le lui transmet). Il signe aussi les liens audio. Les workflows qui parlent au bot reçoivent `BOT_GITHUB_TOKEN` ; sans lui, `podcast.py` s'arrête tout de suite.
  - **Plus de conversation** (depuis 2026-10-26.1) : ni webhook, ni messages, ni Mini App. `lireEtat` oublie une fois ce qu'elle gardait (`ANCIENNES_CLES` : tableau épinglé, assistant, sondages…) et les appareils sans jeton ; `completerConfig` retire l'ancien réglage `livraison`. Premier code : `GET /api/code-connexion[?si=premiere]` demandé par `code_connexion.py` (fin du déploiement tant qu'aucun appareil n'est connecté, workflow « Code de connexion ») et affiché dans le résumé de l'exécution GitHub ; lien `…/app#code=123456`. La nouvelle version s'annonce par notification.
  - Clés saisies dans l'application : gardées par le bot, exportées aux exécutions GitHub (`liaison.appliquer_cles`, masquées dans les journaux) ; elles passent avant les secrets GitHub.
- **Épisodes** (GitHub Actions) : `podcast.py`, avec `regles.py`, `sources.py`, `trains.py`, `recherche.py`, `horaire.py` (filet de sécurité), `pays.py` et `donnees/pays.json` (profils CH, FR, BE partagés avec le bot).
  - Mémoire (`memoire.json`, enregistrée par le workflow) : `charger_memoire` ne garde que les clés de `memoire_vide()` — toute nouvelle clé doit y être ajoutée, sinon elle s'efface chaque jour (c'était le cas d'`articles_vus` avant 2026-10-21.8). `articles_vus` : actus racontées (7 jours), comparées par `meme_sujet` (même sujet sous un autre titre) ; les recherches lisent `lus_pour(n)` articles pour en garder n nouveaux ; les actus des rubriques personnalisées comptent aussi. `lieux_presentes` : déplacements déjà présentés (dates, idées proposées, champ `idees` du script), rappelés dans la section DÉPLACEMENTS.
  - **Prénoms, journées et fêtes** (sans réseau) : `fetes.py` lit `donnees/prenoms.json` et `donnees/journees.json`, fabriqués par `outils/construire_fetes.py` à partir des tables `outils/fetes/*.txt` (prénoms, ONU, fêtes nationales, usages FR/CH/BE, listes tierces de recoupement). Après toute modification d'une table : `python3 outils/construire_fetes.py` (régénère) puis `--verifier` (un test le lance) ; ne jamais éditer les JSON à la main. Choix, biais par pays et limites : `docs/SOURCES-FETES.md`. `donnees/saints.json` reste une source secondaire (mai et juin y avaient été échangés).
  - **Pays** : `donnees/pays.json` (195 profils) est fabriqué par `outils/construire_pays.py` (CH, FR, BE écrits à la main, jamais touchés ; les autres déduits de babel et des fuseaux, marqués `auto`) ; `"--"` = « Pas renseigné » (pas de fériés ni de médias de pays, l'heure reste celle du pays d'avant dans `config.fuseau`). Les jours fériés suivent le pays (`planning.feries_region` est dérivé, sauf le canton choisi en Suisse) ; plus de réglage « Jours fériés de » dans le planning.
  - **Longueur des épisodes** : `memoire.remplissage` (mots écrits / mots visés, borné 0,5 à 1) majore la consigne de longueur donnée à Gemini ; mesuré après chaque épisode (`script_mots_vises`). Nouvelle clé de mémoire déjà déclarée dans `memoire_vide()`.
  - **Mémoire des rubriques** : l'événement `episode` porte `rubriques` ({id: titre, texte, sources}) ; le bot garde les 30 derniers passages par rubrique (stockage `rub:<id>`), les sert à GitHub (`GET /api/rubrique?id=`) et à l'application (actions `rubrique_resume`, `resume_podcast`). La synthèse est `recherche.resume_rubrique` (format `resume` du workflow Recherche) et revient par l'événement `resume` (`etat.resumes`, clé audio `resume:<id>`). Agendas : `agenda.retires` (ceux du secret GitHub qu'on retire de l'application ; aussi dans `exclus`).
- **Voix** (`config.js`, section « voix et animateurs ») : chaque voix Gemini est un animateur possible, sous son nom ou le prénom donné (`voix.noms`) ; `voix.inactives` = voix coupées ; les deux habituels (`voix.animateurs`, `nom` toujours recopié de la voix) ne peuvent pas être coupés ; `voix.jours` = deux places par jour (`""` = habituel, résolu par `placesDuJour`) ; « au hasard » tire parmi les voix activées. Prénoms uniques au sens de `identifiant()` de `podcast.py`, jamais le nom d'une autre voix. Application (actions `nom_voix`, `voix_active`, `voix_jour`) et demandes libres (`nommer_voix`, `activer_voix`, `desactiver_voix`, `voix_jour`) passent par les mêmes fonctions. Les configurations d'avant 2026-10-21.10 (équipe, tirage, jours par prénom) sont converties par `completerVoix`.
- **Application** : genre de chaque rubrique (`genreRegle` dans `miniapp.js` ; icône et couleur : `GENRES` dans `app.html`). Calendrier du planning : mois en cours + 12, seuls les jours hors habitude sont envoyés (`jourCalendrier` complète côté page). Accueil : toucher « Prochain épisode » ouvre l'onglet Épisode réglé sur ce jour (`S.jourVue.deroule`) ; « Annuler » le dernier changement est dans Réglages. Fiche d'un épisode : Sources et Texte se replient (`S.replis`, `enteteRepli`). Voix : une ligne par voix (prénom, timbre raccourci, bouton rond lecture ou téléchargement, interrupteur).
- **Déploiement** (`deployer-bot.yml`) : tests, `wrangler deploy`, puis `cloudflare/secrets.mjs` transmet au bot `GEMINI_API_KEY` s'il ne l'a pas, et `BOT_GITHUB_TOKEN` comme `GITHUB_TOKEN`.

## Tests

- Bot : `cd cloudflare && npm ci && npm test` (wrangler dev sur 8799, faux services `test/faux.mjs` sur 8790 ; arrêter un aperçu en cours avant). `app()` passe par le jeton d'un appareil de test, connecté par code au début (reconnecté d'office si un scénario le retire).
- Python : `pip install -r requirements.txt`, puis `python tests/test_podcast.py` et `python tests/test_regles.py`.
- Aperçu : `node test/apercu.mjs [reglages.json]` dans `cloudflare/`, puis le lien affiché (il contient un code de connexion).
- Les tests tournent aussi sur GitHub à chaque envoi.
- Journaux GitHub Actions : `gh run view --log` ne marche pas ici ; lire les annotations (`gh api repos/…/check-runs/<job>/annotations`). `mise_a_jour.py` y laisse d'où vient son jeton et son résultat (notices).
